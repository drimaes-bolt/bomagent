# 01. 프로젝트 정의

> **시작도 뿌리도 BOM이다.** 다봄은 여러 부서의 업무로 넓어지지만, 모든 기능은 하나의 일에서 나온다. 회로설계 엔지니어가 쓴 E-BOM에 재고 리스트 같은 SCM 정보를 합쳐 양산용 M-BOM으로 자동 변환하고, 양산이 끝날 때까지 관리하는 일이다(1.6 뿌리 원칙, DEC-18).
>
> 다봄은 연구소 E-BOM을 사내 기준정보(품목·재고·거래처·후보 부품)에 맞춰 M-BOM으로 바꾸고, 양산이 끝날 때까지 변경을 추적하는 사내 시스템이다. 협력사 NC AI는 표기를 읽고 판단하는 모델을 만들고, 드림에이스는 그 모델을 쓰는 규칙·도구·화면·기록을 만든다. 확정은 언제나 사람이 한다.

## 1. 이름

### 1.1 결정 [제안 · DEC-01]

| 대상 | 이름 |
|---|---|
| 시스템(사용자 호칭) | **다봄** (DaBOM). 정식 표기는 "다봄 · 전사 BOM 변환·추적 시스템" |
| 약칭 | 다봄(DaBOM) 또는 BOM Agent. 문서와 화면에서는 '다봄'을 먼저 쓰고 'BOM Agent'는 병기·약칭으로 쓴다(DEC-01 보충, 2026-11-24) |
| 파생 프로젝트 | **다봄 구축 프로젝트** (Project DaBOM, 코드 `DABOM`) |
| 협력사 모델 | NC AI BOM 도메인 모델 (NC AI 문서의 'NCAI 도메인 모델') |
| 개발 구조 용어 | 오케스트레이터(에이전트 계층). 개발 문서에서만 쓴다 |
| 상위 협업 | 드림에이스 × NC AI BOM AX 협업 |

### 1.2 'BOM Agent'를 바꾸는 이유

1. 무엇을 하는 시스템인지 이름에 없다. '에이전트'는 개발 구조 용어라 회계·구매 담당자에게는 따로 설명이 필요하다.
2. '대리인'처럼 들려 시스템이 알아서 결정한다는 기대를 만든다. 실제 원칙은 '확정은 사람이 한다'이다(R02 1.3.4, R05 0장).
3. 협력사 모델, 기존 드림에이스 대시보드, 다봄 내부의 에이전트 계층이 모두 '에이전트'로 불리면 회의에서 대상이 섞인다.

### 1.3 '다봄'의 뜻

- 현장에서 BOM을 '봄'으로 읽는다. 다(모두) + 봄(BOM)이다.
- 이 시스템의 약속 두 가지를 담는다. 모든 부서가 같은 BOM을 본다(R02 1장의 단일 마스터와 부서별 뷰). 원문부터 변경 이력까지 다 보인다(R04 0장의 개정 추적).
- 부르기 쉽다. "다봄에 올려 주세요", "다봄에서 확인해 주세요".
- 이름 속에 뿌리가 들어 있다. '봄'은 BOM이다. 'BOM Agent'로 불러도 가운데 낱말은 같다. 기능이 아무리 늘어도 이름이 가리키는 곳은 BOM 하나다(1.6).

### 1.4 검토한 다른 이름

| 후보 | 장점 | 채택하지 않은 이유 |
|---|---|---|
| BOM 브릿지 | 연구소와 생산·구매를 잇는다는 뜻이 바로 보인다 | 변경 추적과 전 부서 공유가 드러나지 않는다. 흔한 이름이다 |
| BOM 원장 | 모든 변경이 장부처럼 남는다는 뜻이 있다 | 회계 장부로 오해하기 쉽고 변환 기능이 드러나지 않는다 |
| 같이봄 | '함께 본다'는 뜻이 더 직접적이다 | 구어체이고 길다 |
| BOM 허브 | 중심 시스템이라는 뜻이 있다 | 일반 명사에 가깝고 하는 일이 드러나지 않는다 |

> 사내 명칭으로 쓰는 데는 제약이 없다. 외부 출시나 상표 등록을 할 때는 상표 검색을 따로 해야 한다. [판단]

### 1.5 명명 체계

| 대상 | 규칙 | 예 |
|---|---|---|
| 모듈(사용자 메뉴) | 한국어 이름 + 내부 코드 3자 | 가져오기(`IMP`), 맞추기(`MAT`), 만들기(`BLD`), 품번(`COD`), 확정(`CFM`), 추적(`TRK`), 알림(`ALR`), 원가(`CST`), 기준정보(`MDM`) |
| 기능 | 모듈 코드-번호 | `MAT-03` 사양 동등 기존 품목 검색 |
| 단계 | n단계 + 이름 | 0단계 준비, 1단계 초안, 2단계 확정, 3단계 추적, 4단계 확산 |

**기존 문서와의 대응** · 'BOM Agent', 'BOM 에이전트', '지능형 BOM Agent', '드림에이스 애플리케이션', 'Agent Application'(R01~R03)은 모두 다봄을 가리킨다. 사용자는 'BOM Agent'도 약칭으로 쓴다(DEC-01 보충, 2026-11-24). R02 7장의 'Foundation Model & Inference 계층'은 NC AI BOM 도메인 모델이다.

### 1.6 뿌리 원칙: 시작도 뿌리도 BOM이다 [제안 · DEC-18]

다봄은 이 기획이 다루는 여러 부서의 업무를 자동화한다. 그 확장은 넓다. 그래도 출발점은 하나다. 회로설계 엔지니어가 쓴 설계 BOM(E-BOM)과 재고 리스트 같은 SCM 정보를 취합해 양산 BOM(M-BOM)으로 자동 변환하고, 양산이 끝날 때까지 관리하는 일이다. 모든 일이 이 일에서 시작했고, 이 일에 닿아 있다.

```text
 뿌리   BOM   E-BOM(설계) + SCM 정보(재고·거래처·구매 이력) → M-BOM(양산), 개정과 변경 이력
   │
 줄기   처음 만든 기능   가져오기 → 맞추기 → 만들기 → 품번 → 확정 → 추적   (IMP MAT BLD COD CFM TRK)
   │
 가지   부서별 확장      원가 CST · 알림 ALR · 생산 준비 PRD · 품질 확인 QLT · 이후 더할 기능
        (기준정보 MDM은 줄기가 맞춰 보는 사내 데이터를 관리하며 줄기를 받친다)
```

| 층 | 무엇 | 다봄에서의 뜻 |
|---|---|---|
| 뿌리 | BOM. 원문 E-BOM, M-BOM 개정, 품목·구조, 변경 패키지 | 모든 부서가 같은 BOM을 본다. 데이터는 하나다(원칙 9) |
| 줄기 | E-BOM → M-BOM 변환과 양산 종료까지의 추적 | 가장 먼저 만든다. 1~2단계의 중심이다 |
| 가지 | 부서별 기능. 원가·알림·생산 준비·품질 확인과 앞으로 늘 기능 | BOM에서 읽고, 결과를 BOM에 돌려주거나 BOM 옆에 목록으로 낸다 |

**확장 규칙** [제안]

1. 새 기능·화면·모듈은 "BOM의 무엇을 읽고(입력), 무엇을 BOM에 돌려주는가(출력)"를 한 줄로 적는다. 적는 곳은 [docs/04 1.1 BOM 뿌리 지도](04_기능_범위.md)다.
2. 한 줄로 적을 수 없는 업무는 다봄의 기본 범위 밖이다. 버리는 것이 아니라 미결(`OI-nn`)로 올려 범위를 사람이 정한다.
3. 가지가 늘어도 줄기의 원칙(5장 1~10)이 그대로 적용된다. 원문 보존, 확정은 사람, 계산은 규칙이다.
4. 가지는 BOM에서 목록·계산·대조까지 하고, 실행은 ERP·MES·품질 시스템에 맡긴다. 4장의 '하지 않는 것'이 이 경계다.

**이 규칙으로 지금까지의 판단을 다시 본다** [판단]

- 범위 밖으로 둔 항목(4장 '하지 않는 것', [docs/14](14_부서기능_확장검토.md) 7장)은 대부분 "BOM에서 목록·계산까지만 하고 실행은 다른 시스템이 한다"는 모양이다. 수입검사는 대상 목록까지, 불출은 불출 목록 계산까지, 발주는 견적 필요 목록까지다. MSL 개봉 시간 추적은 현장 실행(MES)의 일이라 범위 밖이었고, BOM에서 읽을 입력도 없다.
- 반대로 `MAT-12`(E-BOM 없이 재고 열람)는 BOM을 쓰기 전에 BOM이 맞춰 볼 사내 품목을 먼저 보는 입구라서 들어왔다. 입력이 BOM 행이 아니라 BOM이 맞춰 볼 대상이라는 점이 다르다. 이 차이는 1.1 표에 적었다.

> 이름이 'BOM Agent'였다가 '다봄'이 되었어도 이 뿌리는 바뀌지 않는다. 두 이름이 공유하는 낱말이 BOM이다.

## 2. 배경 — 무엇이 문제인가

### 2.1 현장 진술

- 같은 시트를 부서마다 다르게 읽는다. 그래서 E-BOM과 M-BOM이 따로 논다(R01 1장).
- 가장 큰 병목은 엔지니어가 E-BOM에 적은 표기를 구매가 MPN으로 해독하는 일이다. 드림에이스는 이 일이 자동화되면 M-BOM 작성 시간이 1/10 수준으로 줄 것으로 기대한다(R01 1장).
- CAD에서 내보내는 BOM의 99%가 엑셀이고, 세 번만 오가면 어느 파일이 진본인지 알 수 없다(R01 2.1).
- M-BOM은 최종 산출물이 아니라 '양산 중이거나 양산 예정인 제품의 최신 상태'다. 양산 뒤에도 여러 번 개정된다(10/16 미팅, `references/samples/NCAI전달_Readme_261019.txt`).

### 2.2 데이터로 확인한 문제 [관측]

| 문제 | 근거 | 출처 |
|---|---|---|
| 설계 BOM에 MPN이 없다 | KK 계열 5개 파일 877행 중 MPN 열이 있는 파일은 1개 | R03 1.2 |
| 미실장 표기가 많다 | `NC` 표기 103행(11.7%) | R03 1.2 |
| 같은 부품이 표기마다 갈린다 | KK1 한 장에 100nF가 10가지 표기, 합계 131개 | R04 2.5 |
| 'M-BOM'도 확정본이 아니다 | Refine 페어의 M-BOM 시트에서 17행(7.9%)이 품번 미정 | R04 1.3 |
| ERP 코드와 사양이 어긋난다 | 부품 품번 347개 중 17건(4.9%) 불일치. 그중 4건은 다른 사양의 자리를 차지한다 | R05 5.4 |
| 대체 품목 재고가 소요 계산에서 빠진다 | BOM과 연결되지 않은 대체·변형 품목 재고 3건 | R05 5.7 |
| 거래처 변경이 기록 없이 일어난다 | E51K 설계 BOM(2026-05-31)과 ERP 추출본을 품번으로 대조하면 309행 중 45행의 거래처가 다르다(법인명 표기 차이는 제외). 예: DIODES 품목 29행이 소닉슨 → 길라닉스 | 2026-10-19 직접 대조 |
| 한 제조사에 몰려 있다 | Refine M-BOM의 MPN 확정 198행 중 Walsin 87행(43.9%) | R04 2.4 |

거래처 45행이 실제 전환인지 기록 차이인지는 두 파일만으로는 알 수 없다. 어느 쪽이든 언제, 왜 바뀌었는지가 남아 있지 않다. 이 공백이 다봄이 풀 문제다.

### 2.3 협력사 설계에서 비어 있는 부분

NC AI의 변환 설계(2026-10-02 회의 자료, R06·R07)는 E-BOM 행 하나를 분류 → 사양 해석 → 후보 판정을 거쳐 11열 평면 M-BOM 행으로 만드는 **한 번의 변환**을 다룬다. 다봄이 채울 부분은 다음과 같다.

- 개정 추적: 변경 층·사유·효력·재고 처분·승인
- ERP(Amaranth) 모·자품번 구조와 ERP 코드
- 사내 재고·거래처·후보 부품을 쓰는 매칭(NC 설계는 유통사 검색과 가정 수준의 선호 제조사만 쓴다)
- 회계·생산 관점: 원가, LOSS, 공정 구분
- 기구·Set 조립 품목: NC 설계의 경로 ④는 비구매 행과 기구 행을 함께 발주 제외로 둔다. 실제 M-BOM에서 라벨·브래킷·FFC·LCD는 ERP 코드와 거래처가 있는 구매 품목이다
- 평가셋과 수용 기준

## 3. 목표

### 3.1 정성 목표

1. 연구소가 E-BOM을 올린 그날, 사내 품목·재고·거래처를 반영한 M-BOM 초안과 확인 요청 목록이 나온다.
2. 모든 부서가 같은 최신 M-BOM을 보고, 무엇이 왜 바뀌었는지와 그 영향(재고·원가·일정)을 함께 본다.
3. 부품 종류와 신규 품목 등록이 늘지 않는다. 사내에 있는 것을 먼저 쓴다.
4. 사람의 판단과 교정이 기록으로 쌓여 다음 판단과 협력사 모델 개선에 다시 쓰인다.

## 5. 설계 원칙

| # | 원칙 | 뜻 | 근거 |
|---|---|---|---|
| 1 | 원문을 지우지 않는다 | 원본 E-BOM 파일과 행을 보존하고 모든 변환을 원문과 잇는다 | R06 파싱 단계, KK 샘플의 원본 시트 보존 |
| 2 | 확정은 사람이 한다 | 모델은 판단을 돕는다. 자동 확정은 사내 이력과 완전히 일치할 때만 한다 | R02 시나리오 A 검증 노트 |
| 3 | 틀리면 안 되는 것은 규칙으로 | 채번·수량·원가·안전 차단은 결정론으로 처리하고 모델 산술을 막는다 | R03 2.1, 태스크 정의 T-12 |
| 4 | 모델에는 단가·재고·거래처 조건을 보내지 않는다 | 영업비밀을 보호하고 시점에 따라 바뀌는 정보를 분리한다 | R07 화면 원칙, R03 2.4 |
| 5 | M-BOM은 상태다 | 개정·단계·기준선·변경 패키지로 관리한다 | R04 0·6장 |
| 6 | 사내 것을 먼저 쓴다 | 지정 부품 → 기존 품목(재고 보유 → 사용 이력) → 후보 풀 → 거래처 카탈로그 → 외부 후보 순서(DEC-13) | R02 시나리오 E |
| 7 | 모든 값에는 출처가 있다 | 근거·신뢰도·확인자를 남기고 빈 값과 모름을 구분한다 | R03 2.2 |
| 8 | 경계에서 멈추는 것이 정상 동작이다 | 구조 확정·반제품 품번·L1 변경은 사람에게 넘긴다 | R02 1.3.4, RB-ST-08 |
| 9 | 화면은 부서별, 데이터는 하나 | 같은 개정을 부서별 뷰와 권한으로 본다 | R02 1.2 |
| 10 | 한 번에 바꾸지 않는다 | 섀도 운영 → 제안 → 조건부 자동. 기존 엑셀 업무와 병행한다 | R03 D-M |
| 11 | 모든 확장은 BOM에서 뻗는다 | 기능이 부서별로 넓어져도 시작과 뿌리는 BOM이다. 새 기능은 BOM의 무엇을 읽고 무엇을 돌려주는지 적는다(1.6) | DEC-18 [제안] |

| 5 | 변경 패키지와 승인 경로(층 × 시장) | 협력사 설계는 한 번의 변환만 다룬다 | 07 |

| 7 | ERP 등록 경로 | NC 설계의 출력은 11열 평면 목록이다. 실제 ERP는 모·자품번 22열 구조다 | 05 5·6장 |
| 8 | 권한과 데이터 경계 | 단가 마스킹, 모델 입력 제외 항목, 협력사 전달 데이터 등급이 필요하다 | 05 7장, 06 7장 |
| 9 | 결정 기록과 교정 로그 | 사람이 한 판단을 다시 묻지 않게 하고, 협력사 모델 개선 데이터로 쓴다 | 06 8장 |

| 12 | 기구·Set 조립·펌웨어 품목 처리 | 회로 부품만 다루면 완제품 BOM이 되지 않는다 | 02, 08 7장 |
