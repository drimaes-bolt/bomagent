# 06. 시스템 구조와 모델 역할

> 다봄은 화면, 워크플로, 오케스트레이터, 규칙 엔진, 커넥터, 저장소로 이루어진다. NC AI 모델은 그 바깥에서 API로 호출되며 분류·사양 해석·후보 판정만 한다. 틀리면 안 되는 계산과 차단은 규칙 엔진이 하고, 확정은 사람이 한다.

---

## 1. 구성

```text
┌────────────────────────────────────────────────────────────────────────┐
│ 화면       부서별 뷰 · 업로드 · 확인 요청함 · 승인함 · 개정 비교 · 원가 요약 │
└───────────────┬────────────────────────────────────────────────────────┘
┌───────────────▼────────────────────────────────────────────────────────┐
│ 워크플로·상태 관리   BOM 개정 상태(S0~S6) · 변경 패키지 · 승인 라우팅 · 알림 │
├────────────────────────────────────────────────────────────────────────┤
│ 오케스트레이터(에이전트 계층)  경로 결정 · 컨텍스트 구성 · 모델 호출 · 검증·환산 │
├──────────────────────────────────┬─────────────────────────────────────┤
│ 규칙 엔진                         │ 커넥터                               │
│ 룰북 RB-* · 채번 규칙 · 동등 판정   │ ERP 추출 적재 · Amaranth 등록 파일    │
│ 수량·원가 계산 · 결정론 검증기      │ 유통사 API · 통보 수집 · 메일·메신저  │
├──────────────────────────────────┴─────────────────────────────────────┤
│ 저장소   원본 파일 · BOM 개정 · 기준정보 사본 · 후보 풀 · 결정 기록 · 로그    │
└───────────────┬────────────────────────────────────────────────────────┘
                │  JSON 스키마 · 무상태 호출 · 단가·재고·거래처 조건 제외
┌───────────────▼────────────────────────────────────────────────────────┐
│ NC AI BOM 도메인 모델 (API)   분류 · 사양 해석 · 후보 판정 (+ 협의 태스크) │
└────────────────────────────────────────────────────────────────────────┘
```

| 구성 요소 | 하는 일 | 비고 |
|---|---|---|
| 화면 | 부서별 뷰, 업로드, 확인 요청함, 승인함, 개정 비교, 원가 요약 | 권한별 마스킹([docs/03 7장](03_부서별_활용.md)) |
| 워크플로·상태 관리 | BOM 개정 상태, 변경 패키지 상태, 승인 라우팅, 알림 | 모든 상태 전이를 기록 |
| 오케스트레이터 | 처리 경로 결정, 컨텍스트 구성(분류 목록·관례 발췌·결정 기록·그래프 조회), 모델 호출, 응답 검증(스키마·근거 ID)과 단위·코드 환산 | NC AI 흐름도의 '에이전트' 레인과 같다(R06) |
| 규칙 엔진 | 룰북(S·H·L 등급), 채번 규칙, 사양 동등 판정, 수량·원가 계산, 결정론 검증기 | 프롬프트가 아니라 코드로 구현한다(R02 5.7 노트) |
| 커넥터 | ERP 추출 적재, Amaranth 등록 파일 생성, 유통사 API, 통보 수집, 메일·메신저 | 외부 전송을 모두 기록 |
| 저장소 | 원본 파일, BOM 개정, 기준정보 사본, 후보 풀, 결정 기록, 사전·룰북 버전, 로그 | 원본은 지우지 않는다 |

## 2. 처리 경로

NC AI 설계(R06 그림 1)는 행을 네 경로로 나눈다. 다봄은 이를 이어받되 ④를 둘로 나눈다.

| 경로 | 대상 | NC AI 설계 | 다봄 |
|---|---|---|---|
| ① 사양 → 후보 탐색 | 사양만 적힌 행 | 해석 → 후보 판정 | 맞추기 순서 0~4를 먼저 적용하고, 사내에서 못 찾을 때만 외부 후보 판정 |
| ② 지정 품번 검증 | 품번이 적힌 행 | 유통사 조회 → 검증 | 사내 품목 동일 MPN을 먼저 조회 |
| ③ 미실장 | NC 행 | 발주 제외 | BOM사용여부 미사용, 필요수량 0으로 M-BOM에 남긴다 |
| ④ 비구매 | 테스트 포인트·패드·고정 홀 | 발주 제외 | 발주 제외, M-BOM에 남기거나 뺀다(규칙 기준) |
| ④' 기구·Set 조립 | 라벨·브래킷·나사·FFC·LCD·팬 모터 | ④와 함께 발주 제외 | **구매 품목**으로 처리한다. ERP 코드·거래처를 붙이고 제품 레벨에 둔다(DEC-12) |

|---|---|---|---|

## 4. 모델 인터페이스

### 4.1 현재 설계 — NC AI 스키마 0.2 (R06·R07)

| 태스크 | 입력 | 출력 | 다봄 후처리 |
|---|---|---|---|
| `classify_row` 분류 | 행 원문(열 → 셀 값), 분류 목록, 관례 발췌. 품번만 있는 행은 유통사 조회 결과를 더한다 | 분류(분류 ID · `unknown` · `non_purchase`), 차선 후보, 원문 근거, 상태(`resolved` · `open`), 근거 ID | 경로 결정. 미확정이면 확인 요청 |
| `interpret_row` 사양 해석 | 행, 분류별 속성 정의·단위, 그래프 사실, 관례·결정 기록 | 속성별 원문 문자열(환산 전), 상태(`resolved` · `assumed` · `open` · `not_applicable`), 확인 요청(차단 여부) | 단위·코드 환산. 차단이면 멈추고, 결정 기록을 반영해 다시 호출 |
| `select_part` 후보 판정 | 정규화 사양, 값·사이즈로 1차 선별한 후보, 선정 정책·룰북 발췌, 제조사 별칭 표 | 후보별 판정(`satisfies` · `conditional` · `undetermined` · `unfit`), 속성별 판정, 정책 효과(`prefer` · `warn` · `require_approval`) | 정렬(적합 → 사내 선호), 구매 선택 요청 |

### 4.2 인터페이스 원칙 (양사 합의 대상)

1. **무상태 호출.** 매번 완성된 입력 한 벌을 보낸다. 앞선 대화에 기대지 않는다(R07).
2. **단가·재고·납기·거래처 조건을 입력에 넣지 않는다**(R07, DEC-03).
3. **출력은 JSON 스키마로 강제한다.** 형식 강제(제약 디코딩)는 NC AI 요구사항으로 둔다(R03 2.2).
4. **모든 판단에 근거를 붙인다.** 원문(관측 문자열·열 이름)과 근거 ID가 없는 값은 계약 위반으로 본다.
5. **모르면 기권한다.** `open`·`undetermined`는 오답으로 세지 않는다(R03 2.3).
6. **환산은 다봄이 한다.** 모델은 원문에서 고른 문자열을 내고, 단위·EIA 코드 환산은 다봄이 한다(R06 Task 2).
7. **버전을 남긴다.** 스키마·모델·사전·결정 기록 버전을 행의 근거에 기록한다.
8. **호출 기록을 보관한다.** 요청·응답·지연·모델 ID. 학습 데이터로 넘기는 범위는 OI-10에서 정한다.

### 4.3 추가 협의 태스크 후보 [제안]

NC AI 설계 문서는 학습을 진행하면서 태스크와 입출력이 바뀔 수 있다고 밝혔다(R06 1장). 아래 후보는 그 조정 과정에서 협의한다.

| 후보 | 필요한 이유 | 지금 대안 | 우선 |
|---|---|---|---|
| 동일 부품 판정(T-05) | 표기 변형·포장 접미사(L3 함정, R04 1.4)를 같은 부품으로 묶고, 시제·양산 품번은 묶지 않는다(R04 A9) | 정규화 규칙 + 사람 확인 | 높음 |
| 비구매·기구 구분 | 경로 ④가 구매 품목인 기구까지 발주에서 빼지 않게 분류를 나눈다 | 다봄 규칙(대분류·키워드) | 높음 |
| 변경 분류 | 개정 차이나 요청문에서 변경 층(L1~L4·정정)과 사유 코드 후보를 제안한다 | 사람 분류 | 중간 |
| 통보문 해석 | PCN·EOL·가격 인상 통보에서 대상 MPN·시리즈·일자를 뽑는다 | 사람 입력 | 중간(3단계) |
| 설명 문장 생성 | 변경 사유와 영향을 승인자가 읽을 문장으로 요약한다 | 템플릿 | 낮음 |

## 5. 모델이 하지 않는 일

| 하지 않는 일 | 이유 | 근거 |
|---|---|---|
| 부품 선정·확정 | 최종 선택은 사람(구매)의 권한이다 | R06 3.3, R01 2.2 |
| 수량·소요량·원가 계산 | 같은 입력에 같은 출력이 나와야 한다 | 태스크 정의 T-12 |
| ERP 코드 자리 변환 | 모델이 자리 코드를 만들면 자릿수 착오를 그대로 재현할 수 있다 | R05 6.2 |
| 제품·반제품 품번, 구조 확정 | 실체와 권한의 문제다 | R02 1.3.4, RB-ST-08 |
| 단가·재고·거래처 판단 | 입력하지 않는다 | DEC-03 |
| 안전 규칙의 최종 판정 | RB-SF·RB-DP·RB-ST는 모델 신뢰도와 상관없이 규칙이 막는다 | R02 5.6 |

## 6. 처리 시간

[관측] NC AI 데모 기록(R07)에서 행당 모델 호출은 1~4회였고, 한 행에 약 9초에서 4분이 걸렸다. 범용 대형 모델을 임시로 연결한 결과다. 이 속도면 300행 E-BOM에 몇 시간이 걸린다.

| 대책 | 내용 |
|---|---|
| 규칙 우선 | 동일 MPN, 사내 이력 일치, 비구매 패턴 행은 모델을 부르지 않는다 |
| 결정 재사용 | 같은 표기에 같은 결론이면 결정 기록과 캐시로 다시 쓴다 |
| 묶음 처리 | 같은 표기의 행을 묶어 한 번 해석한다. 묶음이 동일 부품 병합 판정을 깨지 않게 한다(R03 N-E) |
| 병렬 호출 | 행 단위 독립 호출을 병렬로 보낸다 |
| 모델 라우팅 | 쉬운 행은 작은 모델, 어려운 행만 큰 모델로 보낸다(R03 N-O) |

목표 처리 시간은 1단계 실측 뒤 정한다(NFR-04).

## 7. 배포와 보안

- 다봄은 사내망에 둔다.
- 모델은 NC AI API로 쓴다. 서빙 위치(NC AI 측·사내·폐쇄망), 동시 접속, 응답 시간, 사용료는 OI-11에서 정한다. NC AI는 온프렘·폐쇄망·NPU 환경에 맞출 수 있다고 밝혔다(R01 2.6).
- 모델로 나가는 데이터는 최소화하고 전송 기록을 남긴다. 단가·재고·거래처 조건은 입력 생성기가 아예 다루지 않게 해 구조적으로 빠지게 한다.
- 유통사는 공식 API만 쓰고, 약관·호출 한도를 조달 조건과 함께 검토한다. 스크래핑은 쓰지 않는다(R02 시나리오 B 검증 노트).
- NC AI 모델이 나오기 전에 외부 범용 모델을 임시로 쓰려면 보안 승인이 필요하다(OI-12). 승인 전에는 규칙과 결정 기록만으로 돌린다.

## 8. 학습 피드백 루프

```text
 다봄 운영 ──▶ 호출 기록 · 결정 기록 · 교정 로그 ──▶ 등급 분류·가공 (기밀 실값 제외, 합성 표시)
    ▲                                                           │
    │                                              계약 범위 안에서 NC AI에 전달 (OI-10)
    │                                                           ▼
 교체 승인 ◀── 골든셋·레드팀 회귀 시험 ◀──────────────── NC AI 모델 개정
```

- 교정 로그 필드: 행 ID, 태스크, 모델·사전 버전, 모델 출력, 사람이 확정한 값, 교정 유형(수락·수정·거절·상위 보고), 사유 코드(드롭다운, CR 코드 체계와 연결), 처리자, 시각(R03 D-C, R04 6.2).
- 평가셋에 든 행은 학습 전달에서 뺀다(R03 2.3).

## 9. 자율성 단계 A0~A3 [제안 · DEC-09]

R03 D-M의 L0~L3와 같은 단계다. 변경 층 L1~L4와 헷갈리지 않게 A로 표기한다.

| 단계 | 동작 | 다음 단계로 가는 조건 [가안] |
|---|---|---|
| A0 섀도 | 모델·규칙 결과를 기록만 하고 사람은 기존 방식으로 일한다 | 골든셋 필드 정확도·오답률 기준 충족([docs/09 6장](09_검증_평가.md)) |
| A1 제안 | 화면에 제안을 보여 주고 사람이 채택한다 | 채택률·교정률을 측정했고 오답 유형이 안정됐다 |
| A2 조건부 자동 | 사내 이력과 완전히 일치하고 신뢰도가 기준 이상인 행만 자동 확정하고 사후 표본을 확인한다. 나머지는 제안 | 오발주 유발 0건 유지, 표본 감사 합격 |
| A3 예외 중심 | 미결·차단·H 등급만 사람에게 보낸다 | KPI 목표 달성 |

- 단계는 기능별로 따로 올린다. 예를 들어 가져오기는 A2, 맞추기는 A1일 수 있다.
- 어느 단계에서도 사람이 하는 일: 새 제조사 선택, 구조 확정과 제품·반제품 품번, 신규 ERP 코드 승인, L1 변경 승인, S 등급 규칙 해제, 효력·재고 처분 결정.

## 10. 기존 시스템과의 관계

| 시스템 | 관계 |
