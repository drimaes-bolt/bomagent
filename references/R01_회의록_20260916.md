## 1. 요약 (Executive Summary)

1. 현장의 BOM은 시트 자체는 단순하나, 부서(설계·구매·생산·품질·PCB 외주)마다 해석·관리 열이 달라 EBOM과 MBOM이 이원화되고 오류가 누적됨. 이 레거시가 AX 도입의 병목.
2. 가장 큰 실무 병목은 **엔지니어가 EBOM에 임의로 적은 부품 표기를 구매팀이 해독해 MPN으로 매핑하는 작업**. 자동화 시 MBOM 작성 시간이 1/10 수준으로 단축될 것으로 드림에이스가 기대.
3. NC AI는 산업 도메인 CPT(1회) + BOM 에이전트 세부 태스크별 파인튜닝으로 접근. 기업 고유 규칙·암묵지(리드타임, 지정 부품 등)는 모델이 아닌 RAG/툴로 처리하고 모델은 최종 판단을 담당.
4. **BOM 에이전트가 메인 플로우에서 수행할 상위 레벨 사용자 시나리오가 아직 합의되지 않음** → 드림에이스가 정리해 전달하면 NC AI가 이를 바탕으로 9/29 설계안 제안.
5. 현재 샘플 데이터는 실데이터 기반(가격만 조정)이나 양이 적어 학습에는 부족 → 추가 데이터(타 프로젝트 BOM, 계층형 BOM, 원본 EBOM–MBOM 페어, 판매 가능 데이터) 확보 필요.

## 2. 논의 내용

### 2.1 제조 현장 BOM 운영 실태 (드림에이스 설명)

- BOM 시트 자체는 대/중/소분류·코드·수량이 매핑된 단순한 시트. 그러나 구매·생산·연구소·개발·라인 PC 담당자까지 하나의 시트를 각자 방식으로 해석하여 사람 간 관계에서 오차·오류가 발생.
- 전체 흐름: EBOM(설계, 엔지니어링) → MBOM(제조, 구매·PCB 외주까지 연동) → 발주 → 입고 → 양산·재고. 두 BOM 확정 후 발주가 진행되며, 여기서 오차가 없어야 공장에서 결품 없이 생산 가능.
- EBOM vs MBOM ("두루마리 휴지" 비유): 같은 자료를 설계는 정면(스펙·전압·전류·동작온도 중심), 구매는 옆면(가격·납기·사이즈 중심)에서 봄. 수기/엑셀 관리로 실시간 동기화가 안 되어 결국 별개 자료로 취급. 싱크 회의가 필요하나 커뮤니케이션이 길어 틀어짐. SAP 등 ERP를 쓰는 대기업은 나름의 솔루션이 있으나 대부분 업체는 그렇지 않음.
- 이상적 흐름은 MBOM에서 부품 부재·단가 불일치로 교체가 생기면 EBOM에 피드백하는 것이나, 실제로는 따로 노는 경우가 많음.
- CAD에서 export 시 99%가 엑셀(CSV는 생산장비 직결 시에만). 구매팀이 엑셀에 열을 추가하면서 자료 이원화가 시작됨. 세 번만 왔다 갔다 하면 어느 버전이 진본인지 알 수 없게 됨.
- 통합관리 시트(EBOM+MBOM 통합)는 우수한 담당자가 임의로 만든 것으로, 실제 이 수준으로 관리하는 업체는 드묾. 노란색 영역=개발·생산·품질용, 주황색 영역=구매·자재용.
- 현장 방문 인사이트(NC AI): 현대차 1차 벤더 다품종 소량 생산 공장은 BOM 자체가 없고 재고관리도 없이 사람이 손으로 셈(부품 종류 1,000개 이상). 자동화·로보틱스 이전에 BOM·재고관리가 시작점이라는 데 양측 공감.

### 2.2 핵심 실무 병목: 부품 표기 해독과 MPN 매핑

- 엔지니어는 EBOM의 파트넘버/파트네임에 디스크립션 수준의 표현(값, 사이즈 등)을 임의로 기입. 전자부품 BOM은 원래 제조사·스펙·가로/세로/높이까지 기재되어야 하나 설계자가 친절히 쓰지 않음.
- 구매팀이 이를 해독해 MPN(제조사 부품번호)으로 변환. 해석 오류가 발생하며, 제조사 부품번호 규칙은 인터넷에 공개돼 있으나 정확히 이해하는 구매팀은 거의 없음.
- 예시: 같은 저항값이라도 앞 모델 숫자가 다르면 규격(0603 = 0.6×0.3mm)이 다름. `R0603`이 구매팀에는 부품 코드지만 PCB 업체에는 규격으로 읽히는 등 부서별 해석 차이 존재.
- 단위 표기 혼재(0.1µF = 100nF)를 인지 못하면 같은 부품을 두 줄로 나눠 주문하는 사례가 많음 → 동일 부품 병합 기능 필요.
- 제조사 선택은 구매팀 권한. 엔지니어는 스펙만 정하고 삼성/일본/중국 업체 중 선택은 구매팀이 가격 기준으로 결정. 혼용 가능 부품이 많으며, 특정 제조사 필수인 경우만 명시. 후보가 3개면 에이전트는 "그중 하나를 고르면 된다" + 해당 회사가 주로 쓰는 제조사를 기억해 추천하는 수준이면 1차 도움이 됨.
- 실제 사용되는 제조사 범위는 제한적: IC 업체는 수백 개지만 AP·프로세서는 4~5개 업체만 사용. 디지키 등록 부품 중 10% 이내. 삼성·현대기아 협력사는 지정 부품만 사용하므로 범위가 더 좁음 → 이런 정보는 변동 가능하므로 RAG로 처리.
- NC AI 제안 플로우: 엔지니어 표기 해독 → 정규화된 파트 디스크립션으로 저장 → 디지키/마우저 등에서 MPN 후보 검색 → 회사 선호 제조사 반영해 MPN 확정. (마우저=대분류 정보, 디지키=상세 스펙·데이터시트 PDF)

### 2.3 코드 체계·표준·온톨로지

- 드림에이스가 임의로 신규 코드 체계를 작성했으나, 제조사·고객사마다 기존 코드가 다르므로 신코드–구코드 매칭 코드가 함께 부여되어야 함. 4가지 정도 스타일을 리서치했는데 코드 규칙이 모두 달라 온톨로지 필요성에 양측 공감.
- NC AI는 ECLASS를 BOM 도메인 표준 후보로 검토 중. ECLASS의 고유 ID는 ECLASS가 자체 분류 체계에 매긴 ID이며 제조사 제품 ID(MPN)와는 별개. → NC AI 추가 확인 예정.
- MPN은 완전 고유값이므로 온톨로지에서 기업별 다양한 코드를 MPN에 매핑 관리하는 것은 용이. 중요한 것은 파트 디스크립션 정규화. 코드 스타일은 대체로 하이픈·숫자·영문 조합이라 규칙성을 찾을 수 있을 것으로 봄(실제 레퍼런스가 많을수록 좋음).
- 온톨로지의 기대 역할: 기업마다 다른 코드·형식을 정규화·표준화하는 피벗. 자체 문법이 없는(엑셀·수기·전화로 운영하는) 기업에는 세팅 자체를 제안해주는 방향도 검토.
- ID·숫자 하나 어긋나면 에이전트 동작에 문제가 되므로 데이터 관리는 온톨로지 레벨에서 매우 엄격하게, 모델은 이를 잘 가져다 쓰는 구조로.

### 2.4 대체품 시나리오

- 대체 사유: 약 80%가 납기, 20%가 규제. 납기가 10일에서 32주로 급변하는 사례가 있으며, 이 경우 즉시 대체 필요.
- 현재 방식: 담당자가 영업사원 네트워크에 대체품을 요청하고 답을 기다림. 가장 중요한 것은 **대체품을 찾아야 하는 타이밍을 알려주는 것**(예: "관련 대체품 납기 24주, 6개월 후 재고 소진 예상 → 미리 대응").
- 부품·모델별로 납기와 양산계획·출고 일정이 다르므로 대체 타이밍도 다름(예: 3D Vision에는 A 부품 100개, ATTI AI에는 30개).
- 드림에이스 대시보드(약식 자료)에는 대체 필요 항목 알림, 유통 업체에 대체품 확인 메일 발송 기능이 있으며, 모델 가시화 시점에 맞춰 고도화 예정(개발팀과 협의).
- 단순 API(옥토파트·디지키·마우저) 호출이 아니라, 대체 가능 여부·필요 수량·발주/입고 일정 정합성까지 가공된 형태로 제공되어야 함. 드림에이스는 부품 정보 DB와 대체품 도출 방법을 보유.
- NC AI 관점의 역할 분담: 모델은 툴 호출 여부 판단과 최소 스펙(정격 전압·저항 등) 조건 충족 여부 판단을 내장 지식으로 수행. "특정 업체 부품은 8주 전 발주"류의 수시 변동 정보는 암묵지로서 검색 가능한 도구로 구성하고 둘을 결합해 최종 판단.
- 드림에이스 부품 DB를 모델에 내장할지, 소싱·서치 필요 시 호출할지는 NC AI가 검토.

### 2.5 모델 학습 전략 (NC AI 설명)

- CPT: 산업 도메인 전반 지식(교과서·전문 지식, 디지키 제품 페이지의 데이터시트 PDF·도면·사이즈·제조사 정보 등)을 학습. GPU 비용 때문에 CPT는 산업 도메인당 1회만 수행하고, 이후 BOM 에이전트 세부 태스크에 맞춰 파인튜닝. 전장(자동차 전자부품)이 1순위 도메인이며, 완전히 BOM에만 특화된 모델이 아니라 제조 산업 전반을 이해하는 모델을 지향.
- 기업 특수 규칙("우리 회사는 이렇게 쓴다")은 모델이 아니라 에이전트가 입력 시 참고 데이터로 제공. 드림에이스 자료가 CPT에 적합한지, 파인튜닝/RAG 단계가 적합한지는 NC AI가 데이터 검토 후 판단.
- 성능 지표: 드림에이스가 제시한 수치는 특화 모델 가정 하의 이상적 목표이며, 모델+에이전트 결합 시 최종 골로 두고 학습을 병행하며 조정.
- 데이터 양: 학습에 투입 가능한 양은 매우 크므로 많을수록 좋음. 현재 샘플 수준은 CPT에 큰 의미가 없으며, 데이터가 없으면 "검색해서 읽고 처리하는" 방식만 학습 가능.
- 데이터시트 PDF 라이선스: 디지키 등 웹에 공개된 자료는 문제 없음(제조사 내부용 시트는 별도).
- 드림에이스 기존 테스트: EXAONE 3.5(30B급 추정)를 로컬로 띄워 챗봇 테스트 → 범용적·무관한 답변(할루시네이션). 도메인 지식 부족이 원인으로 판단.
- 드림에이스 전달 자료: ① 통합관리 시트(샘플, 실제 양산 프로젝트 기반, 가격만 인위 조정) ② 규격문서(교과서 개념: 대/중/소분류 코드와 영문·국문명, 패키지 동의어 예: SOT-23을 업계별로 다르게 부르는 사례, 위험요소) ③ 테스크 정의서(모델이 길을 헤맬 때 참고용, 우선순위 낮음). 노하우·암묵지가 포함된 데이터는 예외 케이스로 지속 업데이트.
- 멀티레벨 BOM: 현재 샘플은 회로 BOM 단층. 실무에서는 통합 시트 하나로 대부분 충분하나, 기구물 포함 시 3계층 정도의 계층형 BOM 존재 → 드림에이스가 별도 정리.
- 입력 형식: 모델 입장에서는 엑셀보다 CSV가 유리(엑셀은 사람 확인용). 엑셀이 와도 변환하여 투입.

### 2.6 제공 방식·사업 논의

- 모델은 API 형태로 제공 예정. 서빙 GPU는 NC AI가 내부 확보 필요. API 사용료 등 상업 조건은 미논의.
- 모델 사이즈·속도·비용은 트레이드오프. 고객 사정(온프렘, 폐쇄망, NPU, 동시접속 수)에 맞춰 커스텀 가능하며, 베이직/프로 등 티어 구성도 가능. 추론 전용 GPU는 학습용보다 저렴.
- 데이터 구매: 협업이라도 무상 제공이 어려운 드림에이스 고유 데이터가 있다면 NC AI가 구매 비용을 협의할 의사 있음. 드림에이스 내부 논의 후 제안 요청.
- 향후 확장: 전자부품 → 기구·사출 등 타 영역으로 확장 가능성. 학습 결과를 보며 확장 범위 협의.
- 협업 방식: 트레이닝 중 도메인 전문가와 밀착 협업이 필요할 수 있어 드림에이스 인원의 NC 상주(파견) 가능성 언급(NC 측 좌석 4석 여유).

| D1 | **BOM 에이전트 상위 레벨 사용자 시나리오 정리 (최우선)** | 메인 플로우 기준으로 "어떤 사용자(구매/설계/생산/품질)가 어떤 상황에서 에이전트에 무엇을 묻고, 어떤 출력을 기대하는가"를 케이스별로 정리. 단계가 짧아도 무방. NC AI가 예시로 든 후보: EBOM 표기→MPN 매핑, 500대 생산 시 부품 소요량 산출, 부품 EOL 시 영향 제품(where-used) 조회, 차량 등급 대체품 추천, 대체 시 대당 원가 변동, 고가 부품 대체 제안. 이 중 실제 현장에서 필요한 것과 우선순위를 표시. |
| D2 | 예외 케이스·암묵지 룰북 | 표준 플로우에서 벗어나는 케이스, 자주 하지 않더라도 크리티컬한 위험 요소(리드타임 규칙, 지정 부품, 동의어·단위 표기 등)를 룰북 형태로 정리. 이후 지속 업데이트. |

| D4 | 원본 EBOM–정답 MBOM 페어 데이터 | CAD export 직후의 정제되지 않은 원본 BOM(엔지니어가 최초 기입한 표현 그대로)과 구매팀이 MPN 매핑을 완료한 MBOM을 페어로 제공. 연결성이 있으면 최상, 없어도 따로따로 있는 페어라도 유효. MPN 매핑 자동화 학습의 정답지로 사용. |
| D5 | 계층형(멀티레벨) BOM 샘플 | 기구물이 포함된 3계층 수준의 BOM을 별도 표로 정리하여 제공. 회로 BOM과 기구 BOM 구조 차이도 설명 포함. |
| D6 | 판매 가능 데이터 목록 | 협업 범위에서 무상 제공이 어려운 드림에이스 고유 데이터(부품 DB, 대체품 정보 등) 중 판매·라이선스 가능한 항목을 내부 논의 후 제안. NC AI 구매팀과 협의 진행. |

| D8 | 회의 자료 HTML 버전 공유 | 회의 중 시연한 자료(대시보드·플로우 자료)의 HTML 판 전달. | 즉시 |

| D10 | 대시보드 고도화 요구사항 (참고) | 모델 가시화 타임라인에 맞춰 개발팀과 대시보드 고도화 계획 수립. NC AI 모델 API 호출 방식·기대 출력 형식을 함께 정의. |
